## Generated Android, Wiki, and `file_reader_test`

The release wheel was installed in clean temporary environments. The tests did
not use an editable generator checkout. They pinned:

- official Supernote plugin template
  `af3f36f6d6f61d9dbd153b0ebb444a3d3621d25f`;
- Wiki revision `da2ab8afeb416d2695206d36d3e628cd620420fe`;
- `file_reader_test` revision
  `9f626ed39be82b43ff74eb735d10b7de61f51508`.

The generated Android test created the C++ and Kotlin examples from the README,
verified template synchronization, and checked that a second update changed
nothing. JavaScript linting and TypeScript checking passed. Gradle, KSP, Kotlin,
CMake, JNI, and JSI all compiled, and the official plugin build and package
verifier passed.

The Wiki test checked the documented commands and outputs, ran its public CLI
scenario, confirmed that `check --build` did not change the source, and produced
a package accepted by the official verifier.

The pinned `file_reader_test` test passed non-migration scenarios 7.1 through
7.7 and checked the saved results for scenarios 7.9 and 7.10 again. It also
built and verified the real plugin package. Separate NOTE and DOC fixtures were
created from the 15 checks in the source manifest. Both were linted,
type-checked, compiled through the Android native and JVM stack, packaged, and
verified. CI saved the packages for that exact commit, but it did not run them
on a tablet. The earlier NOTE and DOC tablet results are covered below.

## Tests using the published PyPI package

After publication, two clean machines installed `sn-module-gen==0.1.0` directly
from PyPI:

- **macOS ARM64, Python 3.9:** checked the version, help, schema resource, and
  sole `sn-module-gen` command; created the pinned official template; generated
  a mixed C++/Kotlin feature; checked template synchronization and a no-change
  update; then passed `--json check --build`, `npm run build`, and
  `npm run verify`.
- **native Ubuntu x86_64, Python 3.12:** repeated the PyPI package, pinned
  template, mixed-feature, Android build, and package-verification tests with
  Node 20 and Java 17.

GitHub-hosted native Windows passed the platform path, lock, subprocess,
symlink, PowerShell/template, fake-ADB, and `npm run run` tests. The additional
PyPI test on the `z-force` Windows machine was skipped and **did not run**. The
macOS and Linux results do not replace that missing test.

## Tablet testing

[`maintainers/device-evidence/`](../device-evidence/README.md) contains the
tablet tests run before the public release. Some filenames and text still use
the V4 development name. They are left as recorded so the commands, identities,
and hashes remain accurate.

The release workflow parsed the saved lifecycle, NOTE, and DOC results again
and checked them against the source manifests. This checks that the saved
records still match the test definitions. It does **not** mean that the final
release commit, wheel, or tag was installed and run on a tablet. No new tablet
test was performed during publication or cleanup.

Those results only apply to the listed Nomad firmware, PluginHost version,
plugin identities, files, and permission choices. They do not guarantee the
same result on every Supernote model, firmware, PluginHost build, or permission
state.

## Post-release cleanup

After the production package and host smokes passed, all ten pre-public versions
of the legacy PyPI distribution `supernote-module-generator` were yanked:

```text
1.0.0
2.0.0, 2.0.1, 2.0.2, 2.0.3, 2.0.4
3.0.0, 3.0.1, 3.0.2, 3.0.3
```

All 20 legacy files use the exact yank reason:

```text
Pre-public development package; replaced by sn-module-gen
```

The old PyPI project and files were kept, and no redirect package was published.
An unpinned package lookup returned no matching distribution. An exact version
pin can still select a yanked file, which is normal PyPI behavior.

The ten matching old GitHub releases and tags were deleted. The public `v0.1.0`
release and tag and the unrelated `v1-final` tag were kept. After cleanup, the
remote contained only the annotated `v0.1.0` tag, which points to the release
commit, and `v1-final` at
`e6402d6992da2b4a621ac2007d069224b163284c`.

## What was not tested

- These results apply only to the exact release commit, tag, files, workflow
  inputs, and environments listed above.
- The GitHub-hosted Windows tests are not the skipped PyPI test on `z-force`.
- Fake ADB tests the launch command, not a real device.
- Compiling Android code and verifying a `.snplg` package do not prove that
  PluginHost loaded or ran it.
- The earlier tablet records were checked again, but the final release commit
  and public wheel were not run on the tablet.
- Compatibility, conversion, and migration from pre-public generated layouts
  were not tested or promised.
- No result is claimed for Python versions, operating systems, filesystems,
  Android toolchains, hardware, firmware, PluginHost versions, or permission
  choices that were not tested.
