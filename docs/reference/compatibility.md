# Compatibility matrix

This is the canonical compatibility page for the generator. “Generated” means
the Python tool can create files; it does not mean the parent plugin compiled,
PluginHost loaded the result, or a device executed it.

The released baseline is `1.0.0`; this page also describes unreleased
`1.1.0.dev0` source changes and evidence reviewed on 2026-08-01. Main-branch
documentation may describe unreleased changes; use
`supernote-module --version` and the matching Git tag when diagnosing an older
installation.

## Development tools

| Component | Required or recommended | Enforcement/evidence |
| --- | --- | --- |
| Python | **Required:** 3.9+ | Package metadata and CI cover 3.9–3.13. JNI/JSI Android builds also invoke `python3` for copied code generation. |
| React Native | **Required by current official Supernote template:** 0.79.2 | Official Supernote guide says the host/template must match 0.79.2. Generated Gradle reads the parent installed version but the generator does not reject another version. |
| Node.js | **Official recommendation:** current LTS, at least 18 | Doctor checks only that `node --version` succeeds. No real npm/Yarn plugin fixture is built in this repository's CI. |
| npm | Supported selection; no version pinned | Doctor checks availability. Lifecycle unit tests simulate npm; an end-to-end install is not in CI. |
| Yarn | Supported selection; no version pinned | Doctor checks availability. Lifecycle unit tests simulate Yarn; modern Yarn variants are not qualified. |
| Java/JDK | Generated bytecode/toolchain target: 17; Doctor accepts Java 17+ | Current official Supernote environment page recommends JDK 19+. The interaction between that parent requirement and the generated Java 17 toolchain needs a real template build; Doctor success alone is not proof. |
| Android SDK | **Required:** platform 35; official guide also calls for Build-Tools 35.0.0 | Generated projects use `compileSdk 35`; Doctor checks `android-35/android.jar` but not Build-Tools 35.0.0. |
| Minimum Android API | Generated modules use `minSdk 27` | Template constant; not a published Supernote device-support promise. |
| Android NDK | **JNI/JSI required:** an NDK whose Clang accepts C23 and C++23 for API 27 arm64 | Doctor runs compiler probes; no NDK revision is pinned. |
| CMake | **JNI/JSI required:** 3.22.1+ | Enforced by generated Gradle/CMake and checked by Doctor. |
| ABI | **JNI/JSI:** `arm64-v8a` | Generated Gradle filters to arm64. Other ABIs are not generated or tested. |

Use the official [Environment Setup](https://docs.supernote.com/en/environment)
for the parent plugin, then use Doctor for generator-specific checks:

```bash
supernote-module doctor --type native
supernote-module doctor --type jni
supernote-module doctor --type jsi
```

## Host operating systems

| Host | Status |
| --- | --- |
| Linux | Python suite runs in GitHub Actions on Python 3.9–3.13. This is not an Android/plugin packaging build. |
| macOS | Python suite and installed-wheel generation smoke passed during the 2026-08-01 review. The source checkout contained spaces; the temporary target plugin did not. A complete `.snplg` build was not run. |
| Windows | Code contains Windows/PowerShell and `gradlew.bat` branches, but CI has no Windows job and path behavior is not qualified. Treat support as expected, not tested. |
| Paths with spaces | The generator source checkout works from a path with spaces. A plugin root containing spaces and official-template Android packaging remain unqualified. |
| Non-ASCII paths | Not covered. Use an ASCII plugin path until a real cross-platform fixture qualifies this. |

## Supernote device and module status

No official device/firmware matrix for this generator exists. The official
developer guide describes the PluginHost architecture and current React Native
`0.79.2` template, but generator documentation must not infer
support for every Supernote model or firmware from that alone.

| Capability | Generation | Repository compile/package proof | Device/runtime status |
| --- | --- | --- | --- |
| Kotlin/Java module | Implemented | Generated shape and KSP source are unit-tested; no official-template build/package in CI | Fits the officially described Java/TurboModule capability, but this generator has no published per-device qualification. |
| Kotlin/Java + JNI module | Implemented | Binding generation is tested; no official-template Android compile/package in CI | Fits the officially described Java-to-C/C++ route; exact device/firmware still requires testing. |
| Synchronous JSI module | Implemented | Binding/loader generation is tested; no official-template compile/package in CI | **Experimental and blocked on the tested enforcing retail configuration.** Do not promise retail support. |

## JSI has three separate support gates

1. **Generation:** the generator creates a C++ package, HostFunctions, loader,
   declarations, and autolinking.
2. **Compilation:** the parent project resolves React Native/JSI headers and
   builds the module `.so`.
3. **Execution:** PluginHost resolves its private `libjsi.so`, loads the child
   plugin library, registers the native installer, and SELinux permits execution
   from the extracted plugin directory.

The first gate is implemented here. The second is not in this repository's CI.
For the third, project-maintainer device testing on 2026-07-30 found:

- PluginHost `1.00.26005190`, React Native `0.79.2`, arm64, on two Nomad
  configurations;
- the generated loading pattern worked on a userdebug/permissive tablet;
- an enforcing retail tablet denied execution of the extracted `.so` with
  `dlopen ... Permission denied` / SELinux `{ execute }` denial;
- both configurations lacked the needed execute permission; permissive mode
  merely bypassed the denial.

This aligns with the official [Plugin Principles](https://docs.supernote.com/en/principle),
which currently describe Java/TurboModule capability followed by Java-to-C/C++
and state that direct C/C++ calls from JS/TS are not supported.

Do not use a permissive development-tablet success as retail evidence. Re-test
the exact firmware/PluginHost and enforcing policy before changing this status.

## Documentation freshness

- Released users should read the README/docs from their installed version's Git
  tag when a matching tag exists.
- Unreleased `1.1.0.dev0` source records the generator version in generated
  module metadata and README; the release checklist verifies this marker.
- User-visible changes belong in [CHANGELOG.md](../../CHANGELOG.md).
- Template or compatibility changes require the contributor checklist in
  [CONTRIBUTING.md](../../CONTRIBUTING.md).
- Breaking ownership or metadata changes require migration notes before a
  release.
