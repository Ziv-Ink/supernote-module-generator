## 1. Executive summary

The generator has a sound product model and a better-than-average safety baseline for a young developer tool. The main menu is understandable, destructive removal uses typed confirmation, ordinary package-manager failures roll back parent-project edits, updates preserve user-owned Kotlin/Java and C/C++ sources, validation is explicit about being structural, and all three generated module types could be built after supplying a suitable Gradle test fixture. The generated import model and TypeScript declarations also passed a strict TypeScript smoke test after the Android build regenerated Kotlin declarations.

It is not ready for broad public use without another hardening pass. There are four release-blocking UX/reliability problems:

1. Interrupting `remove` during dependency refresh leaves the project in a split state: the module directory remains, but its dependency and Kotlin Gradle registration are removed. Rerunning `remove` then fails. `update` repairs the state, but the tool neither performs nor explains that recovery.
2. Doctor can print `Ready for this module type.` when `node`, `npm`, and `yarn` all exit nonzero and the Gradle wrapper is not executable. Presence is mistaken for usability.
3. A package-manager process that exits zero without linking the package is reported as `Installed local dependency`; no postcondition is checked.
4. Interactive values are validated only after the user completes the questionnaire, reviews it, confirms it, and enters a `Progress` screen. Invalid input then returns to the main menu and discards all answers.

The TUI is usable today by an experienced developer who knows valid npm, JavaScript, Android, and semantic-version identifiers; runs it from the exact plugin root; does not interrupt package-manager work; and can diagnose Gradle/npm problems independently. First-time users and developers with incomplete Android knowledge will encounter unnecessary dead ends. Automation users get useful exit codes and stderr separation, but lack `--version`, quiet/machine-readable output, explicit skipped-install recovery, and reliable dependency readiness checks.

Verdict: **promising internal/beta tool; not yet public-release quality**. No Critical data-loss bug was reproduced. Three High reliability findings and one High interaction finding should be fixed before release.

## 3. Product and workflow overview

The tool creates and manages local npm/Yarn packages beneath a Supernote React Native plugin's `local_modules/` directory.

| Module type | User implementation | JS call shape | Generator-owned infrastructure |
| --- | --- | --- | --- |
| Native module | Kotlin/Java | Promise-returning values; fire-and-forget void | React Native bridge, KSP processor, annotation, autolinking, declarations |
| Native JNI module | C/C++ | Promise-returning values through Kotlin/JNI | CMake, JNI bindings/registration/loading, Kotlin bridge, declarations |
| JSI module | C/C++ | Synchronous | CMake, JSI HostFunctions/installation/loading, declarations |

Main workflows:

1. `Add module`: choose a type, package/import name, and description; optionally configure namespace, JS module name, and version; review; generate; wire; optionally install the local dependency.
2. `Update module`: select an owned module; replace generator-owned infrastructure while preserving implementation source; refresh linking/dependencies.
3. `Validate module`: check metadata, generated files/bindings, and parent integration. It intentionally does not compile or device-test.
4. `Remove module`: select one/all; show file count and directory; require exact typed confirmation in the TUI; unwire; refresh dependencies; delete module directories.
5. `Doctor`: inspect project, Android, C/C++, Node/package-manager, and deployment prerequisites.
6. `Help`: print a workflow-oriented guide.

The no-argument command is the intended TUI. Subcommands are the automation/compatibility interface.

## 5. Detailed findings

### Installation and first launch

#### F1. The TUI opens in an invalid directory and fails only after an action

- **Severity:** Medium
- **Workflow:** Run with no arguments in `/private/tmp/supernote-module-ux-audit.kNt2WJ`, press Enter on default Add.
- **Observed:** The title falls back to `Create and manage local native Android modules.`; Add then prints `error: Run this command from a Supernote plugin root...` and returns to the same menu.
- **Why it matters:** A first-time user can explore a menu that cannot perform its core actions. The corrective context scrolls away, and the new menu no longer repeats it.
- **Expected:** Detect the invalid root before the main menu. Offer the exact required markers and current directory.
- **Fix:** Replace the menu with: `Not a Supernote plugin root: <cwd>. Expected PluginConfig.json, package.json, and android/. cd to the plugin root and retry.` Doctor and Help may remain available.
- **Locations:** `cli.py:349-360`, `cli.py:421-423`, `integration.py:19-25`.

#### F2. Source checkout works, but packaging/version discoverability is incomplete

- **Severity:** Low
- **Workflow:** `python3 supernote_module.py --version`; direct execution of the file without `python3`.
- **Observed:** `--version` exits 2 and says a command is required. The file has a shebang but lacks executable permission, so direct execution returns shell exit 126.
- **Why it matters:** Users and support scripts cannot identify the running version. The direct execution issue is minor because README correctly says `python3`.
- **Expected:** `--version` prints `supernote-module 0.2.0`.
- **Fix:** Add argparse `action="version"` and include the version in Doctor/help. Optionally mark the launcher executable if direct invocation is intended.
- **Locations:** `pyproject.toml`, `cli.py:1012-1029`.

### Help and discoverability

#### F3. Help omits behavior-changing defaults and recovery details

- **Severity:** Medium
- **Workflow:** `supernote-module add --help`; `add local-x --yes --skip-install`.
- **Observed:** Help does not say omitted `--type` becomes Kotlin in noninteractive mode. `--skip-install` says installation remains pending, but successful noninteractive output never repeats the pending action or exact recovery command.
- **Why it matters:** `--yes` silently commits to a backend, and scripted generation can look complete while the local dependency is not linked.
- **Expected:** Help states `default: kotlin` for noninteractive Add; success states the pending command.
- **Fix:** Show defaults in help and print `Dependency not installed. Next: npm install` or the Yarn equivalent.
- **Locations:** `cli.py:233-234`, `cli.py:1048-1107`, `ui.py:351-376`.

### Command-line argument handling

#### F4. `--skip-install` still requires a package-manager choice

- **Severity:** Medium
- **Workflow:** In a plugin with no lockfile: `add probe-no-manager --yes --skip-install`; equivalent Update and Remove commands.
- **Observed:** All fail with `Could not choose a package manager; pass --package-manager yarn or --package-manager npm`.
- **Why it matters:** The requested operation explicitly will not invoke a package manager. This blocks offline/generation-only use for irrelevant information.
- **Expected:** Do not select a manager when installation/refresh is skipped. Display `Install: skipped`.
- **Fix:** Resolve a manager only inside the non-skipped branch; make summary accept `Skipped`.
- **Locations:** `cli.py:438-459`, `cli.py:548-587`, `cli.py:635-698`.

#### F5. Repeated options silently use the last value

- **Severity:** Low
- **Workflow:** `add local-conflictflag --type kotlin --type jsi ...`; `doctor --type kotlin --type jsi`.
- **Observed:** JSI wins silently.
- **Why it matters:** Duplicated CI variables or copy/paste mistakes can generate the wrong backend.
- **Expected:** Reject conflicting repetitions; identical repetitions may be accepted or warned.
- **Fix:** Use a custom argparse action that records duplicates and rejects differing values.
- **Locations:** `cli.py:1048-1072`, `cli.py:1142-1148`.

#### F6. Automation output lacks quiet and machine-readable modes

- **Severity:** Low
- **Workflow:** Inspect all command help; redirect outputs.
- **Observed:** Streams and exit codes are generally correct, but there is no `--quiet`, `--json`, stable event format, or way to suppress decorative success output.
- **Why it matters:** CI must scrape prose and absolute paths.
- **Expected:** At minimum, `--json` for Doctor/Validate and `--quiet` for lifecycle commands.
- **Fix:** Keep current human output as default; add structured objects with a documented schema.
- **Locations:** parser and print calls throughout `cli.py`/`ui.py`.

### Interactive prompts and navigation

#### F7. Interactive values are validated after confirmation, then discarded

- **Severity:** High
- **Workflow:** TUI → Add → Native module → package `Bad Name` → default description → no advanced options → confirm Add.
- **Observed:** The review displays invalid values, the tool enters `── Progress ──`, then prints `error: Invalid npm package name: 'Bad Name'` and returns to the main menu. All answers are lost.
- **Why it matters:** Users spend time answering dependent prompts and explicitly confirm an action the tool already knows is impossible. The Progress heading implies work began.
- **Expected:** Validate each field immediately, explain the format, preserve other answers, and reprompt only the invalid field. Validate the complete configuration before showing the final review.
- **Fix:** Give `Wizard.text` a validator; run package validation before deriving defaults, then validate derived namespace/module name. Do not print Progress until staging is about to begin.
- **Locations:** `cli.py:228-277`, `cli.py:417-448`, `validation.py:50-74`.

#### F8. Valid values collide with navigation words

- **Severity:** Medium
- **Workflow:** TUI → Add → package/import name → enter `q`.
- **Observed:** The entire application exits. The same applies to `quit`; `b`/`back` navigate away. These are valid npm package names. Descriptions equal to those words are also impossible.
- **Why it matters:** Data fields should not reserve ordinary values without saying so.
- **Expected:** Navigation shortcuts should be explicit commands that cannot collide, such as `:q` and `:back`, or only active in selection menus.
- **Fix:** In free-text fields, recognize only `:quit`/`:back` or handle Esc/Ctrl+C. Do not treat bare words as commands.
- **Locations:** `ui.py:42-50`.

#### F9. Back means “main menu,” not “previous question”

- **Severity:** Low
- **Workflow:** TUI → Update → select module → enter `b` at `Update this module?`.
- **Observed:** `↩ Back to main menu`; selection cannot be revised in place. README's general `Esc goes back` wording suggests a navigation stack.
- **Why it matters:** Changing one answer requires restarting the workflow.
- **Expected:** Back from review returns to the previous selection/question; Cancel returns to main.
- **Fix:** Model the wizard as steps or relabel the shortcut `Esc cancel to main`.
- **Locations:** `cli.py:1186-1204`, `ui.py:303-312`.

### Input validation

#### F10. Valid npm names can produce invalid inferred identifiers with no recovery hint

- **Severity:** Medium
- **Workflow:** `add 123 ...`, `add 1abc ...`, `add class ...`, `add probe.a.b ...`.
- **Observed:** Errors are about the derived Android namespace or JS module name, not the input relationship. No error suggests `--android-namespace` or `--module-name`. `probe.a.b` derives an invalid JS name containing periods.
- **Why it matters:** The package name itself satisfies the generator's npm regex; users cannot infer why a separate default failed.
- **Expected:** Derive legal identifiers deterministically or ask for/identify the exact override.
- **Fix:** Sanitize punctuation into word boundaries, prefix numeric identifiers, avoid Java/Kotlin reserved segments, and say: `Derived module name "…" is invalid; use --module-name NAME`.
- **Locations:** `cli.py:130-153`, `validation.py:60-74`.

#### F11. Package length is not validated and filesystem errors leak through

- **Severity:** Medium
- **Workflow:** Add a 215-character name, then a 256-character name.
- **Observed:** 215 characters is accepted despite npm's package-name limit; 256 reaches `error: [Errno 63] File name too long: '<...>/.supernote-module.json'`.
- **Why it matters:** Long generated class/library/path names may fail later on other platforms. The raw errno does not state the accepted maximum.
- **Expected:** Reject overlong package names before filesystem work with a specific limit.
- **Fix:** Enforce npm length and generated filename/path budgets, including Windows constraints.
- **Locations:** `validation.py:8-52`.

#### F12. Invalid-name messages reject correctly but teach too little

- **Severity:** Low
- **Workflow:** uppercase, spaces, Unicode, emoji, RTL, slash, backslash, apostrophe, shell metacharacter, reserved word, Java/Kotlin/JS keywords.
- **Observed:** Most are safely rejected before writes, but `Invalid npm package name: ...` does not show the permitted grammar or an example.
- **Why it matters:** Users must consult npm documentation or guess repeatedly.
- **Expected:** One-line rule plus example.
- **Fix:** `Use lowercase letters, digits, -, _, ., or ~; scoped form @scope/name is allowed. Example: local-math.`
- **Locations:** `validation.py:50-74`.

### Error handling

#### F13. Ctrl+C and Ctrl+D produce internal tracebacks

- **Severity:** Medium
- **Workflow:** Ctrl+C on the main menu; Ctrl+D at Package/import name.
- **Observed:** Full Python stack traces from `KeyboardInterrupt` and `EOFError`; exit 1.
- **Why it matters:** Routine terminal controls look like crashes and expose implementation details. During mutating phases this also bypasses rollback.
- **Expected:** `Cancelled; no changes were made.` or phase-aware recovery output, exit 130 for SIGINT and a documented EOF exit.
- **Fix:** Catch interrupts at the outer boundary and around transactions; restore terminal state and transactional snapshots before returning.
- **Locations:** `ui.py:144-176`, `ui.py:42-50`, `cli.py:1186-1228`.

#### F14. Permission and filename failures are safe but raw

- **Severity:** Low
- **Workflow:** Add in chmod 555 root; use a 256-character name.
- **Observed:** Raw `[Errno 13] Permission denied` and `[Errno 63] File name too long` with long internal paths.
- **Why it matters:** The user is not told which prerequisite/action to fix or whether any files changed.
- **Expected:** Friendly category, path, rollback status, and next step.
- **Fix:** Convert common `OSError.errno` cases into `Cannot create local_modules/...: permission denied. Nothing was changed.`
- **Locations:** `_execute` exception boundary in `cli.py:1160-1182`.

### Cancellation and recovery

#### F15. Ctrl+C during Remove leaves a broken split state

- **Severity:** High
- **Workflow:** `remove local-math --package-manager npm --yes` with a long-running npm; interrupt during `npm install`.
- **Observed:** `package.json` dependency and Gradle marker are removed; module directory remains. `validate local-math` reports both missing integrations. Rerunning Remove fails with `package.json does not contain dependency local-math`. `update local-math --skip-install --yes` repairs it.
- **Why it matters:** A standard interruption breaks the parent build and the obvious retry path. This is the closest reproduced issue to project corruption.
- **Expected:** Restore parent snapshot on interrupt, or delete only after refresh and record a resumable transaction. Recovery must be printed.
- **Fix:** Catch `BaseException` narrowly for `KeyboardInterrupt`/`EOFError` around the transaction, restore the snapshot, and verify it. Add an idempotent Remove path that tolerates already-absent integration.
- **Locations:** `cli.py:684-704`; `except Exception` at `cli.py:699` excludes `KeyboardInterrupt`.

#### F16. Ctrl+C during Add leaves an unlabelled “install pending” project

- **Severity:** Medium
- **Workflow:** `add local-interrupted --type kotlin --package-manager npm --yes`; interrupt during npm.
- **Observed:** Traceback; generated module, dependency entry, and Gradle wiring remain and validate structurally. Repeating Add says it already exists and suggests Update. No message says installation is pending.
- **Why it matters:** The state is recoverable but ambiguous; users may assume partial/corrupt generation.
- **Expected:** Either roll back, or intentionally commit generation and print `Module created; dependency installation was interrupted. Run npm install or update ...`.
- **Fix:** Treat generation and installation as explicit transaction phases and report which committed.
- **Locations:** `cli.py:441-466`, `integration.py:171-192`.

#### F17. Normal dependency failures roll back correctly

- **Severity:** Positive control
- **Workflow:** Add and Remove with npm absent from PATH.
- **Observed:** Exit 2 with a clear missing-command error. Add removed its new module and parent edits. Remove restored dependency and Gradle wiring and retained the directory.
- **Why it matters:** The existing snapshot/restore design is a strong foundation; interrupt handling should reuse it.
- **Locations:** `cli.py:441-463`, `cli.py:684-704`, `generator.py:264-292`.

### Existing-project and overwrite behavior

#### F18. Collision with an unowned directory gives an impossible recovery command

- **Severity:** Medium
- **Workflow:** Create `local_modules/local-unowned/keep.txt`; run Add, then suggested Update.
- **Observed:** Add safely refuses but says `Use update 'local-unowned' instead.` Update then says it cannot find a generator-owned module.
- **Why it matters:** The preservation is correct, but the guidance sends users into a dead end.
- **Expected:** Distinguish owned existing module from unowned collision.
- **Fix:** `Destination exists but is not owned by this generator. Choose another package name or move the directory; nothing was changed.`
- **Locations:** unconditional existence check `cli.py:426-427`; ownership checks `cli.py:484-502`.

#### F19. Update is idempotent and preserves implementation source, but offers no diff

- **Severity:** Medium
- **Workflow:** Modify `Example.kt` and generated `index.js`; Update twice.
- **Observed:** User source survives, generated file is replaced, and duplicate dependency/Gradle entries are not added. The TUI only says `Preserve Kotlin/Java files...`; it does not list replaceable files, show a diff, or mention parent `package.json` reformatting.
- **Why it matters:** The behavior is correct but trust-heavy, especially in a dirty Git worktree.
- **Expected:** A concise planned-change list and `--dry-run`/`--diff`, with a warning when Git is dirty.
- **Fix:** Show create/replace/preserve/parent-edit counts; add dry-run. Do not require backups if atomic staging remains reliable, but state rollback coverage.
- **Locations:** `cli.py:554-591`, `generator.py:142-292`, `integration.py:240-255`.

#### F20. Git state is ignored for destructive actions

- **Severity:** Low
- **Workflow:** Add in a Git repo containing uncommitted/untracked files; inspect Remove path.
- **Observed:** No dirty-worktree warning. Remove warns generically to back up only in generated README, not by inspecting actual state.
- **Why it matters:** Typed confirmation prevents accidents but does not tell users whether source is recoverable.
- **Expected:** Before Update/Remove, show `Git: clean`, `Git: 3 uncommitted changes`, or `not a Git repository`.
- **Fix:** Read-only `git status --porcelain` with a short nonblocking warning.
- **Locations:** lifecycle workflows in `cli.py`; no Git inspection exists.

### Dependency detection

#### F21. Doctor can falsely report Ready with unusable tools

- **Severity:** High
- **Workflow:** Put fake `node`, `npm`, and `yarn` first on PATH; each exits 42–44. Make `android/gradlew` non-executable. Provide a valid React Native directory. Run `doctor --type kotlin`.
- **Observed:** All four tools are `[OK]`; Doctor exits 0 and prints `Ready for this module type.`
- **Why it matters:** Doctor's core promise is readiness. This false positive sends users into later build/install failures and misdiagnoses their environment.
- **Expected:** Execute `node --version`, manager `--version`, and Gradle wrapper `--version`; require zero exit status, parse versions, and report the failing command.
- **Fix:** Make discovery return command health, not just a path. Check executable permission. Preserve stderr/exit code in Doctor details.
- **Locations:** `toolchains.py:42-47`, `toolchains.py:133-140`, `toolchains.py:319-355`.

### Generated output

#### F29. Fresh Kotlin declarations contain an unresolved template token, yet Validate passes

- **Severity:** Medium
- **Workflow:** Add fresh Kotlin module; inspect `index.d.ts`; run Validate before Android build.
- **Observed:** `export interface $MODULE_NAME_RAWModule` is emitted. Validate reports structurally valid. The Android KSP build later replaces it with `MathModule`.

- **Expected:** Fresh file should contain `<ModuleName>Module`; Validate should reject any unresolved template token.
- **Fix:** Use `${MODULE_NAME_RAW}Module` in the template and scan generated text for `$[A-Z_]` placeholders.

- **Expected:** Detect the script and show it only when present; otherwise show a generic build/deploy note or warn it is missing.
- **Fix:** Check `<root>/deploy_plugin.sh` before rendering next steps.
- **Locations:** `ui.py:351-376`.

### Performance and perceived responsiveness

#### F32. Noninteractive dependency work can be silent for up to ten minutes

- **Severity:** Low

### Recommended canonical terminology

- **Local module:** the complete generator-managed package beneath `local_modules/`.
- **Module type:** Native module, Native JNI module, or JSI module.
- **Package name:** npm/Yarn package name and JS/TS import specifier.
- **JavaScript object name:** default-import object/native module identity.
- **Android namespace:** generated Java/Kotlin package namespace.
- **Module directory:** root of one local module.
- **Implementation source:** user-owned Kotlin/Java or C/C++ tree.
- **Generated infrastructure:** replaceable generator-owned files.
- **Plugin root:** invocation directory containing `PluginConfig.json`, `package.json`, and `android/`.
- **Install local dependency:** npm/Yarn linking step.
- **Build and deploy plugin:** separate Gradle/device step.

### Recommended rules for defaults

1. Show every behavior-changing default in both TUI and CLI help.
2. Enter must always select the displayed bracket/highlight default.
3. Never display brackets on typed destructive confirmation; there is no default.
4. Defaults must already pass validation.
5. Derive identifiers only when the result is legal; otherwise reprompt with an editable suggestion.
6. Do not ask for values unused by the selected path (`--skip-install` must not need a manager).
7. Destructive actions default to no or exact typed confirmation.
8. Reversible creation/update may default yes only after a valid, accurate review.
9. A `recommended` label must match the actual highlighted/default result.
10. Noninteractive and interactive defaults should match unless help explicitly explains the difference.
11. Reruns should reuse metadata, not re-derive changed defaults.
12. Success must report pending skipped work and verified postconditions.

## 7. Edge cases tested

### Input values

- Empty CLI name: rejected with actionable required-name example.
- Empty interactive fields: displayed defaults are selected.
- Whitespace-only description: rejected as non-empty requirement.
- Leading/trailing interactive whitespace: silently trimmed; generated `local-ux`.
- Leading/trailing CLI whitespace: rejected.
- Uppercase package name: rejected.
- Lowercase package name: accepted.
- Spaces: rejected in package names.
- Hyphens: accepted and transformed into derived identifiers.
- Underscores: accepted after the first package character; leading underscore rejected.
- Periods: package regex accepts them, but derived JS name can fail.
- Slash: rejected unless valid scoped `@scope/name`; scoped name succeeded.
- Backslash, quotes, apostrophe, semicolon/shell metacharacter: rejected; no shell execution occurred.
- Unicode accented text, emoji, and Hebrew package names: rejected before writes.
- Unicode and spaces in the parent path: succeeded.
- Newline in description: safely JSON-escaped; generated package remained valid.
- Numeric-only and number-leading names: package accepted, inferred Android namespace rejected.
- Java/Kotlin reserved namespace segments: rejected.
- JavaScript reserved module names and numeric module names: rejected.
- C/C++ keyword-style package names were not special-cased; generated identifiers remain subject to JS/Android validation. `nullptr` is valid C23 and was not incorrectly treated as unavailable in the C23 probe.
- Reserved Windows filenames such as `con`: rejected.
- 215-character name: accepted; 256-character name: raw filesystem failure.
- Duplicate package/dependency/module identities: rejected.

### Paths and project shapes

- Empty/non-plugin directory: TUI opens but actions reject.
- Existing Supernote plugin fixture: supported.
- Standard React Native-like package without `PluginConfig.json`: rejected as not a Supernote plugin root.
- Missing `android/`: rejected.
- Missing `settings.gradle`/`.kts`: source inspection confirms rejection; error text names only `settings.gradle`.
- Relative module name and absolute owned module path: accepted.
- Absolute path to a module owned by another plugin: rejected.
- Symlinked plugin root: resolved and worked.
- Read-only root: safe permission failure.
- Unowned file/directory at intended module path: preserved, but guidance is wrong.
- Scoped package directories: supported through nested scope path.
- Dirty Git repository: mutation allowed without warning.
- Java-only/Kotlin-only parent layout: not directly relevant because the module owns its source layout; generated module build was tested.
- Parent CMake/JNI configuration: not modified by Add for local JNI/JSI packages.
- Monorepo/nested invocation: no upward discovery; user must run from exact plugin root.

### Controls and terminal behavior

- Enter on default selections: works.
- Up/down: works and wraps around.
- Escape in raw menus: goes back/exits; searchable lists clear a filter first.
- `b/back` and `q/quit` in line mode: work as navigation but collide with valid data.
- Ctrl+C: traceback.
- Ctrl+D: traceback in line prompt.

- Arrow keys: supported.

- `q` in searchable lists: always quits, so it cannot be part of a filter.

- Rapid/pasted input: line-buffered prompt values can flow into subsequent prompts; no review bypass was reproduced because final confirmation remains.
- Search lists: eight-item page logic exists; one-module and all-module choices were manually exercised.
- 30×10: overflows vertically.
- 160×40: readable.
- `NO_COLOR`, `TERM=dumb`: ignored in TTY.
- Redirected/non-TTY: plain output, no ANSI; no-argument mode exits 2 with guidance.

- Node/npm/Yarn present and healthy: paths detected.
- Node/npm/Yarn absent: Doctor marks missing; lifecycle package operation gives precise missing-command error.
- Node/npm/Yarn present but exit nonzero: Doctor falsely marks OK.

Design principles:

- Fail before mutation.
- Validate at the field where correction is possible.
- Present the minimum decision information; put implementation constraints behind Help.

- Make every mutating phase resumable or rolled back.
- Keep experienced-user subcommands fast, observable, and machine-readable.

## 12. Final verdict

The generator's core architecture is safer and more coherent than its current UX polish suggests: owned-directory checks, staged replacement, rollback for ordinary failures, source preservation, idempotent wiring, precise native export diagnostics, and buildable Kotlin/JNI/JSI output are meaningful strengths.

The public interface still overstates certainty at exactly the moments users most need accuracy. Doctor can claim readiness without runnable tools, dependency installation can claim success without a link, validation can approve an unresolved template token, and interruption can leave Remove half-applied. The TUI also makes ordinary correction expensive by validating after confirmation and discarding answers.

**Release decision: do not present 0.2.0 as generally production-ready yet.** Fix the interrupt transaction, Doctor/postcondition checks, inline validation, and Kotlin declaration token first. After those changes, the remaining work is mostly discoverability, terminal compatibility, and consistency rather than a redesign of the product.
